# SURGE — Sunday KMZ-to-33 kV Network Delivery Plan

**Planning date:** Thursday, 13 August 2026
**Target demonstration:** Sunday, 16 August 2026
**Primary outcome:** upload a KMZ, review its engineering features, and display a
constraint-aware, electrically screened 33 kV collector network with preliminary
pole-type recommendations.
**Scope status:** implementation plan only; this document does not claim the
Sunday outcome is already complete.

## 1. The Sunday outcome

The product path to demonstrate is:

```text
User uploads one survey KMZ/KML
    -> Java safely extracts KML/KMZ geometries
    -> user previews and confirms WTG, substation, road, parcel, and restriction classifications
    -> confirmed features are persisted for one project
    -> Java starts an optimisation job and assembles a complete spatial request
    -> Python generates several radial 33 kV PNC candidates
    -> hard exclusions and soft crossing/land penalties influence A* routing
    -> Pandapower rejects electrically invalid candidates
    -> deterministic scoring recommends the best eligible candidate
    -> Python places and classifies preliminary poles on the selected network
    -> Java returns or persists the selected route and pole GeoJSON
    -> the web map displays WTGs, substation, constraints, 33 kV feeders, and pole types
```

For Sunday, “best” must mean:

> The highest-ranked electrically valid candidate among the bounded candidates
> generated by SURGE, routed under the configured spatial constraints and scored
> using the disclosed weights.

It must not mean a mathematically global optimum, a construction-approved
design, or a route that has been validated against data absent from the upload.

## 2. Required input truth

### 2.1 What the KMZ must provide

At minimum, the confirmed import must contain:

- one or more WTG Point features with stable names/IDs;
- exactly one selected substation Point for the Sunday run; and
- a WTG capacity supplied by the feature or a clearly displayed import default.

To claim road or land avoidance, the project must also contain the relevant
geometries. They may be in the same KMZ or in a companion reviewed import:

- road/track/HT-line/watercourse LineStrings;
- cadastral or ordinary land Parcel polygons; and
- restricted/no-go land Polygon features with any required clearance buffer.

If a KMZ contains only WTG and substation coordinates, SURGE can generate a
network between those points, but it cannot truthfully avoid roads or land it
has never received. Do not silently download or invent missing spatial layers
for the Sunday proof.

### 2.2 Correct constraint semantics

“Avoid roads and land” needs an engineering-safe interpretation:

| Feature | Sunday routing treatment | Reason |
| --- | --- | --- |
| Restricted land, water body, sanctuary, settlement exclusion | Hard exclusion after configured buffer | The route must not enter it. |
| Road, HT/EHV line, watercourse represented as a line | Soft buffered crossing penalty by default | Completely blocking a connected road network can make every route impossible; a controlled crossing may be necessary. |
| Cadastral/ordinary parcel | Soft land-impact penalty | An overhead route necessarily occupies land; minimize affected/expensive land rather than claiming all land is avoided. |
| Feature explicitly confirmed as no-go | Hard exclusion | User intent overrides the default soft treatment. |

The response should disclose crossings and affected parcels. A route may cross
a soft constraint when every lower-cost alternative is worse; it must never
cross a hard exclusion.

### 2.3 Pole-type claim

The Sunday result may recommend these preliminary geometry-based structure
classes:

- `33kV terminal/dead-end pole` at the substation and true feeder ends;
- `33kV angle/tension pole` at route deflections above a configured threshold;
- `33kV tangent/suspension pole` at ordinary intermediate spans.

The UI and output must label these as preliminary. Conductor mechanical loads,
wind zone, terrain elevation, soil/geotechnical data, road-crossing structures,
foundation design, statutory clearances, and detailed structural design are not
available and must not be implied.

## 3. Verified repository baseline

### 3.1 Already implemented and reusable

The following current product infrastructure exists:

- `backend-java/src/main/java/com/power/surge/controller/ProjectAssetController.java`
  exposes KMZ/KML preview, reviewed commit, legacy one-step import, project
  assets, and reference lines.
- `KmzGeoJsonConverter` extracts Point, LineString, and Polygon geometries with
  hardened XML handling and preserves KML folder information.
- `AssetClassifier` and `AssetClassificationRules` classify WTGs,
  substations, roads/reference lines, parcels, restricted areas, and other
  survey features.
- `AssetService` persists confirmed WTGs, substations, reference lines,
  cadastral parcels, and restricted areas into the existing PostGIS schema.
- The web map already accepts `.kmz`/`.kml`, provides a preview/override modal,
  and renders imported assets, parcels, restrictions, and generated routes.
- Python already preprocesses WTG/substation WGS-84 Points into a projected
  CRS, builds a raster `CostSurface`, generates bounded PNC scenarios, routes
  MST edges with A*, refines those routes without cutting across blocked cells,
  runs 33 kV-compatible Pandapower analysis, ranks eligible candidates, and
  returns WGS-84 GeoJSON.
- `app/algorithms/pole_placement.py` already implements deterministic span,
  terminal, angle, and intermediate pole heuristics.

### 3.2 Implemented Python constraint and presentation baseline

The Python service now includes:

- `app/gis/constraints.py`, rasterizing WGS-84 lines/polygons onto a cost
  surface;
- `avoidance_geojson` and `avoidance_buffer_m` on the V1/V2 Python request;
- pole-placement configuration in `OptimisationConfig`;
- pole summaries and WGS-84 `pnc_pole` Point features in the rich Python
  presentation result; and
- focused constraint, API, and presentation tests.

SURGE-PY-021 adds V1 constraint regression coverage and SURGE-PY-022 labels the
hand-authored constraint payload accurately as a Python-contract fixture. The
full Python gate currently reports:

```text
460 passed, 2 environment warnings
```

The Python routing path now distinguishes hard exclusions from soft penalties,
checks endpoints against hard buffered geometry, and reports route-level
constraint evidence. The product path is still incomplete because Java jobs do
not send persisted project constraints, and Java does not consume the rich
Python result containing pole Points.

### 3.3 Exact missing link in the current product flow

Current Java job dispatch is:

```text
persisted WTGs + persisted substations
    -> PythonOptimisationRequest V1
       {request_id, project_id, scenario, wtg_geojson,
        substation_geojson, electrical_params}
    -> Python /api/v1/optimise
    -> PythonOptimisationResponse reads five legacy fields
    -> RouteService persists only LineString route features
    -> web map renders persisted routes
```

It currently does **not**:

- query persisted reference lines, parcels, or restricted areas when a job runs;
- send any constraint GeoJSON or pole configuration to Python;
- carry Python's rich candidate/pole result through the Java DTO;
- persist `pnc_pole` Point features or their type;
- return pole features through the generated-route API; or
- render recommended pole types on the final network layer.

Therefore the Python split alone cannot deliver the complete user-upload-to-map
experience. It can deliver the optimisation capability and proof contract, but
the Java/frontend owner must connect the already-imported project data and rich
result.

## 4. Target architecture and contracts

### 4.1 Keep KMZ parsing in Java

Do not add a second KMZ parser to Python. Java already owns multipart upload,
KMZ/KML extraction, preview, classification, user overrides, and persistence.
Python should continue to receive reviewed, explicit GeoJSON domain inputs.

### 4.2 Spatial request contract

Prefer one explicit collection such as `spatial_constraints_geojson` with
per-feature properties:

```json
{
  "type": "Feature",
  "geometry": { "type": "LineString or Polygon", "coordinates": [] },
  "properties": {
    "constraint_id": "stable-project-id",
    "constraint_type": "ROAD | HT_LINE | WATERCOURSE | PARCEL | RESTRICTED_AREA",
    "routing_mode": "SOFT_PENALTY | HARD_EXCLUSION",
    "buffer_m": 10.0,
    "cost_multiplier": 20.0,
    "source": "KMZ_CONFIRMED_IMPORT"
  }
}
```

For minimum change, the current `avoidance_geojson` field can remain as an
additive compatibility alias, but its blanket hard-block semantics must not be
used for ordinary roads and parcels.

Request validation must reject unknown geometry types, non-finite costs,
negative buffers, malformed features, and a project whose required WTG or
substation falls inside a hard exclusion. Feature ordering must not affect the
raster or result.

### 4.3 Python routing and scoring contract

The candidate flow remains:

```text
reviewed WTG/substation GeoJSON
    + reviewed spatial constraint GeoJSON
    -> projected project data
    -> uniform base cost surface
    -> hard exclusions burned as +infinity
    -> soft road/parcel costs burned as finite multipliers/penalties
    -> deterministic scenario generation and A* routing
    -> route refinement with the same surface
    -> PNC assembly
    -> 33 kV Pandapower analysis
    -> hard electrical feasibility filter
    -> deterministic cohort scoring
    -> recommended result + pole placement + GeoJSON
```

For Sunday, retain the existing feasibility-first scoring dimensions: route
length, electrical loss, cable loading, and voltage margin. State that spatial
penalties shape each A* route but are not yet a full parcel-compensation or
lifecycle-cost objective. Adding constraint-impact cost to cohort scoring is a
stretch only after the end-to-end path is green.

### 4.4 Result contract

The selected rich result must provide one FeatureCollection containing:

- WTG Point features;
- substation Point features;
- `pnc_segment` LineStrings with stable segment and feeder IDs, length, final
  loading/loss telemetry, and `nominal_voltage_kv: 33`;
- `pnc_pole` Points with stable pole ID, feeder ID, sequence, preliminary pole
  class, human-readable recommendation, and distance along route; and
- optionally copied constraint features for one self-contained display layer.

Also return a compact summary containing candidate/recommendation identity,
electrical validity, total route length, pole counts by type, hard-exclusion
violations (must be zero), road crossings, and affected parcel count/length.

## 9. Required end-to-end tests

### Import and classification

- Valid KMZ/KML preview extracts Points, LineStrings, and Polygons.
- WTGs and one substation are correctly classified or user-overridden.
- Road, parcel, and restricted land types survive commit and reload.
- Unknown/unreviewed features do not silently become WTGs.
- Duplicate features and missing WTG capacities follow explicit policy.

### Spatial routing

- Hard exclusion creates blocked cells with its configured buffer.
- A final refined route does not cross a hard exclusion.
- A road/parcel soft penalty can be crossed when necessary and is reported.
- Higher soft penalty selects the lower-impact path in a controlled fixture.
- WTG/substation inside hard exclusion fails clearly.
- No-path result fails the candidate/job honestly.
- Feature order and repeated calls produce the same route.

### Electrical and recommendation

- Nominal voltage is 33 kV in the actual load-flow config and output.
- Every recommended candidate is converged, finite, and electrically valid.
- Invalid candidates remain visible with reasons and cannot win.
- The selected scenario and the displayed route share one candidate ID.

### Pole output

- Every selected feeder has ordered, stable pole IDs.
- Shared junction coordinates are not double-counted.
- True ends are terminal/dead-end, significant bends are angle/tension, and
  ordinary span poles are tangent/suspension.
- Maximum span is respected within numerical tolerance.
- Pole WGS-84 coordinates lie on the selected route.
- Repeated calls return the same pole features and counts.

### Full product

- KMZ upload -> preview -> confirm -> run -> completed job -> map requires no
  manual database or payload edit.
- Roads/parcels/restrictions visible on the map are the ones sent to Python.
- Route and pole output survives the chosen Java return/persistence path.
- A Python outage or impossible route appears as failure, never simulated
  success.

## 12. Risks and fallback

| Risk | Response |
| --- | --- |
| Point-only KMZ contains no constraint geometry | Require companion reviewed layers or demo only point-to-point network without an avoidance claim. |
| All roads/parcels are treated as hard blocks | Separate soft penalties from hard exclusions before integration. |
| Constraint closes every path | Return explicit no-route failure; adjust only documented buffer/policy, never silently ignore it. |
| Pole counts are inflated at shared route endpoints | Complete network-level deduplication before presenting totals. |
| Java V1 response drops pole Points | Carry rich result/versioned FeatureCollection; do not force Points through the LineString-only route parser. |
| Full-stack integration slips | Demonstrate the reviewed Python-contract inputs directly through Python V2 as a fallback, while clearly stating KMZ-to-job transport and fixture provenance are incomplete. |
| “Best” is challenged | Show candidate bounds, weights, feasibility rule, and the exact recommendation reason; avoid global-optimum language. |
| Pole recommendation is overinterpreted | Keep “preliminary geometry-based” in API properties, UI legend, and demo narration. |

## 13. Definition of Sunday done

The requested outcome is achieved only when all of the following are true:

- a user can upload and review a KMZ/KML containing WTGs and a substation;
- the run uses only confirmed, persisted project features;
- relevant roads, parcels, and restrictions are actually transported to
  Python rather than merely drawn on the browser map;
- the recommended network is generated by the real PNC/A*/Pandapower/scoring
  workflow at 33 kV;
- final route segments do not cross hard exclusions;
- soft road/land impacts are disclosed rather than hidden;
- the map displays the recommended route and preliminary pole types together;
- every displayed metric and feature belongs to the same candidate and job;
- identical input produces the same recommendation and stable IDs twice;
- failure/no-route cases do not show a successful demo fallback; and
- the team states the preliminary-design limits honestly.

The shortest critical path is not a new optimiser. It is completing the active
Python constraint/pole slice, transporting the already-persisted GIS layers
through Java, preserving the rich result, and rendering its Point and
LineString features in the web map.
