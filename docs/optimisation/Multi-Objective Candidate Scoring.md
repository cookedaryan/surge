# Multi-Objective Candidate Scoring (PY-027 / PY-029)

The `app.optimisation.scoring` module provides deterministic, multi-objective ranking of engineering candidates. It determines which PNC scenario generated by PY-017 is mathematically the "best" under a configurable policy and provides explainable reasons for its selection.

As of SURGE-PY-027, this module unifies electrical and spatial constructability scoring into a single canonical engine using `CandidateEngineeringMetrics` (from PY-026). The preliminary spatial scorer in `app.algorithms.route_scoring` is retained only for legacy compatibility testing.

As of SURGE-PY-029, the same engine can combine that engineering score with
the lifecycle cost produced by `app.costing.lifecycle`. Each
`EngineeringEvaluatedScenario` atomically carries its electrical result,
engineering assessment, and optional cost assessment, preventing costs from
being paired to the wrong scenario by a separate lookup structure.

## Eligibility Composition

Before scoring occurs, candidates are filtered for hard feasibility. To be eligible, an `EngineeringEvaluatedScenario` must satisfy:
1. **Convergence**: Load flow must have converged.
2. **Electrical Validity**: No overloads or voltage limit violations.
3. **Topology Match**: The load flow result shape must match the source network.
4. **Engineering Metrics**: The canonical `CandidateEngineeringMetrics` must be successfully extracted (which requires valid inputs and pole configuration).
5. **No Hard Spatial Violations**: The candidate must not intersect hard avoidance constraints.
6. **Complete Lifecycle Cost (cost-aware mode only)**: The candidate must have
   a complete `CandidateLifecycleCost`.

Ineligible candidates are disqualified and receive a `total_benefit_score` of `None`. However, they remain in the output to provide visibility into *why* they failed via `disqualifications`.

Candidates are also strictly checked for context mismatch. They must all share the same `comparison_group_id` and `electrical_context_id`. Comparing candidates evaluated under different operating points or with different cable libraries is structurally prohibited.

In cost-aware mode, missing or incomplete costs disqualify only the affected
candidate with `INCOMPLETE_LIFECYCLE_COST`. Otherwise engineering-eligible
candidates must also share currency, catalogue identity and version, catalogue
price basis date, energy price basis date, and cost-model version. If more than
one such economic context exists, the incomparable cohort is disqualified with
`ECONOMIC_CONTEXT_MISMATCH`; it is never partially ranked. The shared context
is exposed as a deterministic SHA-256 identifier computed with Python standard
library facilities.

## Objective Groups and Metrics

Metrics are mapped into four canonical groups (all are **lower is better** except Voltage Margin):

- **Physical**
  - **Route Length (m)**
- **Spatial**
  - **Traversal Cost**: Includes spatial routing penalties. Note that weighting both `ROUTE_LENGTH` and `TRAVERSAL_COST` intentionally double-counts physical distance as part of the routing penalty.
  - **Affected Parcel Count**
  - **Road Crossing Count**
  - **Soft Constraint Overlap Length (m)**
- **Infrastructure**
  - **Physical Pole Count**
- **Electrical**
  - **Active Loss (MW)**
  - **Cable Loading (%)**
  - **Voltage Margin (pu)**: **Higher is better**.

Note: `ENVIRONMENTAL_OVERLAP_M2` is extracted in PY-026 but is explicitly omitted from PY-027 scoring.

## Normalization and Exact Mathematics

Metrics are evaluated across the *eligible* cohort. The min and max values establish the normalization bounds. The system uses a **"higher is better" benefit convention**, where the best possible score for a metric is 1.0 and the worst is 0.0.

For "lower is better" metrics:
`normalized_benefit = (max - val) / (max - min)`

For "higher is better" metrics (voltage margin):
`normalized_benefit = (val - min) / (max - min)`

### Constant Range Behavior

If all eligible candidates have the identical value for a metric (`max == min`), `normalized_benefit = 0.0`. The weight is **not** automatically redistributed.

### Group Mathematics

- `metric benefit = min-max normalized value`
- `MetricScore.weight` = `group_weight × subweight`
- `MetricScore.weighted_benefit` = `metric benefit × MetricScore.weight`
- `group score = Σ(metric benefit × subweight)`
- `total score = Σ(group score × group weight)`

Subweights within active multi-metric groups must sum to `1.0`. An inactive
group (group weight `0.0`) must use all-zero subweights. Group weights must sum
to `1.0`. Boolean, negative, and non-finite weights are rejected at the API and
domain boundaries.

## Scoring and Tie-Breaking

Scores are quantized to `12` decimal places to prevent floating point instability during comparisons.

Eligible candidates are ranked by (in unified mode):
1. `Total Score` (Descending)
2. `Weighted Electrical Contribution` (Descending)
3. `Weighted Spatial Contribution` (Descending)
4. `Weighted Infrastructure Contribution` (Descending)
5. `Route Length` (Ascending)
6. `Active Loss` (Ascending)
7. `Scenario ID` (Ascending)

### Cost-Aware Policy

Lifecycle cost uses the same cohort min-max benefit convention:

`economic benefit = (maximum cost - candidate cost) / (maximum cost - minimum cost)`

When every eligible candidate has the same lifecycle cost, economic benefit is
`0.0` for all candidates and no candidate receives an artificial advantage.
The combined score is:

`final benefit = engineering weight × engineering benefit + lifecycle cost weight × economic benefit`

Cost-aware candidates are ranked by:

1. `Final Benefit` (Descending)
2. `Engineering Benefit` (Descending)
3. `Lifecycle Cost` (Ascending)
4. `Route Length` (Ascending)
5. `Active Loss` (Ascending)
6. `Scenario ID` (Ascending)

This order makes engineering strength the first tie-breaker after the combined
policy score. Lifecycle cost is consulted only when the combined and
engineering scores tie. Zero is treated as a valid lifecycle cost.

## Explainability and Trade-off Disclosure

The recommended candidate is accompanied by structured `RecommendationReason`s:
- **Best-Metric**: Emitted only for positively weighted, nonconstant metrics where the winner achieved the absolute best value.
- **Group-Strength**: Emitted when a group materially contributed (`group weight > 0 AND weighted group contribution > 0 AND group contains >= 1 nonconstant metric`).
- **Trade-off Comparisons**: If the winner performed worse on any positively-weighted metric compared to the *ranked runner-up*, a `TRADE_OFF_ACCEPTED` reason is explicitly emitted.

The winner is also compared against the **baseline scenario** to produce absolute and relative improvement metrics. The baseline is identified uniquely by checking `scenario.parameters.strategy == ScenarioStrategy.BASELINE`.

The V2 API preserves the four legacy raw metric fields and additionally returns
the complete canonical engineering metric set (including the unscored
`environmental_overlap_m2`), group contributions, and structured reason details.
